# Balance simulation — medallion pipeline

Turns the `sim_*` rows the balance-simulation Paper plugin writes into analysis-ready
marts, and publishes them for Grafana.

**Design and rationale:** [`docs/balance-simulation/PIPELINE.md`](../../docs/balance-simulation/PIPELINE.md).
**What produces the input:** [`docs/balance-simulation/DESIGN.md`](../../docs/balance-simulation/DESIGN.md).

```
Postgres sim_*  ──▶  bronze (parquet)  ──▶  silver (parquet)  ──▶  gold (parquet)
                     faithful snapshot      typed, unnested,        marts, deltas
                                            derived skills          vs baselines
                                                                         │
                                                        Postgres sim_gold_*  ──▶  Grafana
```

## Quick start

```bash
cd pipelines/balance-sim
pip install -r requirements.txt

# The Postgres JDBC driver, which the repo's Gradle build has already downloaded.
# Not committed; see "Environment notes" for why it is a local file at all.
mkdir -p lib && cp "$(find ~/.gradle/caches -name 'postgresql-42.7.4.jar' | grep -v sources | head -1)" lib/

# One-time: create the serving tables with their indexes and comments.
psql -h localhost -p 5002 -U user -d betterpvp -f sql/gold_ddl.sql

# On Windows, parquet writes need winutils on HADOOP_HOME -- see "Environment notes".
export HADOOP_HOME=/c/Users/$USER/hadoop && export PATH="$HADOOP_HOME/bin:$PATH"

python -m jobs.cli runs                  # which sweeps exist and their status
python -m jobs.cli all    --run-id 4     # bronze -> silver -> gold, publish
python -m jobs.cli gold   --run-id 4     # rebuild marts only, no re-ingest
python -m jobs.cli diff   --run-a 1 --run-b 4
python -m jobs.cli diff   --run-a -11 --run-b 4   # against the standing baseline
python -m pytest tests -q
```

A **negative** `--run-a`/`--run-b` names the standing baseline for a realm and scenario
rather than a sweep: `-11` is realm 1 `one_way`, `-12` is realm 1 `mutual`. The ids come
from `sim_gold_baseline_run`. This is usually the side you want. The baseline has never
been a single run -- realm 1 `one_way` is run 7 (EQUIPMENT, 93.5% of the cells) plus runs
12 and 14 (SKILLS) -- so naming one run compares against a fraction of it.

Diffs match on **canonical fight identity**, not on `sim_build.fingerprint`: a fingerprint
hashes the weapon key, the literal allocated levels and the target role, none of which
survives BASELINE's reductions, so it cannot tell a build that disappeared from one that is
spelled differently. Both fingerprints are still carried and `spelling_changed` marks the
rows that are one fight under two names.

Then open the **Sim — Gold Balance Explorer** dashboard
(`grafana/provisioning/dashboards/sim_gold_balance_explorer.json`, uid
`betterpvp-sim-gold`). It is generated by `grafana/generate_sim_dashboards.py`; edit
the generator, never the JSON.

## Layout

| Path | What |
|---|---|
| `conf/pipeline.yml` | connections, lake root, derived-skill parameters, quality thresholds |
| `jobs/common/` | config, Spark session, JDBC, expectations + audit log |
| `jobs/bronze/ingest.py` | faithful landing of `sim_*` and a `grafana_config` snapshot |
| `jobs/silver/` | typing, unnesting, engagement shape, derived skills |
| `jobs/gold/` | marts, delta computations, publish to Postgres |
| `dags/` | Airflow DAGs (`balance_sim_medallion`, `balance_sim_diff`) |
| `sql/gold_ddl.sql` | serving-layer DDL |
| `tests/` | the derived-skill model, pinned |
| `lib/` | vendored Postgres JDBC driver |
| `data/` | the lake (gitignored) |

## Configuration

Secrets come from the environment; everything else from `conf/pipeline.yml`.

```bash
export BALANCE_SIM_PG_PASSWORD=...        # source and warehouse
export BALANCE_SIM_WAREHOUSE_PASSWORD=... # only if the warehouse differs
```

Knobs worth knowing:

- `derived_skills.backstab.uptime` — `1.0` models every hit landing from behind. It is
  an upper bound, it is stamped on every derived row, and no mart shows a derived
  figure without it.
- `warehouse.skip_publish` — build a mart in the lake but do not push it to Postgres.
  `matchup` and `rune_set_synergy` are per-matchup rather than aggregated, so on a full
  EQUIPMENT sweep they run to millions of rows (6.51M and 6.42M on run 1) and the JDBC
  write of those two is the slowest step in the pipeline by a wide margin. Clearing the
  list and re-running `gold` publishes them from the parquet already on disk.
- `quality.fail_on_error` — an `error`-severity expectation aborts the layer. Leave it
  on; the point of the expectations is that they stop things.

## Airflow

The jobs import nothing from Airflow, so a machine that only runs transforms does not
need it installed. To schedule:

```bash
pip install "apache-airflow==2.10.3" apache-airflow-providers-apache-spark \
  -c "https://raw.githubusercontent.com/apache/airflow/constraints-2.10.3/constraints-3.11.txt"
export BALANCE_SIM_HOME=/path/to/pipelines/balance-sim
# needs an airflow connection `betterpvp_postgres` for the settled-run check
airflow dags trigger balance_sim_medallion --conf '{"run_id": 1}'
```

Triggered rather than scheduled: a sweep is started by hand and takes minutes to days,
so there is no cadence to cron. `check_run_is_settled` refuses to ingest a run still
in `RUNNING`, because bronze's promise is that it snapshots a source that has stopped
moving.

## Environment notes

Two things about this repo's dev machine that cost an afternoon each, recorded so they
do not have to again.

**PySpark version.** Spark 3.5's Python support stops at 3.11 and the toolchain here
is 3.12, so `requirements.txt` pins **PySpark 4.0**. Spark 4 needs Java 17+, which the
project already requires. Spark 4 also defaults to **ANSI SQL mode**, which is why
`silver/dimensions.py` uses `try_cast` for the config mirror's text values — a plain
cast raises on the first `enabled: true` it meets and takes the layer down with it.

**Windows.** Parquet writes need `winutils.exe` and `hadoop.dll` on `HADOOP_HOME`
(the [WindowsProblems](https://cwiki.apache.org/confluence/display/HADOOP2/WindowsProblems)
wiki page, or `cdarlint/winutils` for a prebuilt pair):

```bash
export HADOOP_HOME=/c/Users/<you>/hadoop   # containing bin/winutils.exe, bin/hadoop.dll
export PATH="$HADOOP_HOME/bin:$PATH"
```

The JDBC driver is vendored under `lib/` and attached with
`spark.driver.extraClassPath` rather than `spark.jars`, for two reasons: Maven
resolution fails with a PKIX error behind an HTTPS-intercepting security suite (same
cause as the Gradle truststore issue this repo already knows about), and `spark.jars`
routes the file through Spark's fetch-and-chmod path, which needs winutils to start
the driver at all.

**Python workers.** PySpark's worker subprocess does not start on this machine — any
`createDataFrame` from local rows dies with `Python worker exited unexpectedly`. Every
transform here is a DataFrame expression the JVM evaluates, so the pipeline is
unaffected, and the two places that would have needed a worker avoid it deliberately:
`Auditor.to_frame` and the tests' `frame` fixture both go through a driver-written
NDJSON file. **Do not add a Python UDF** — it would not run here, and a UDF is also
the one thing that would put this pipeline's transformations back outside the JVM's
reach.
