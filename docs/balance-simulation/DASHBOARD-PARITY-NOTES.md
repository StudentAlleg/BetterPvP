# Sim dashboards — parity, permutations, skill scope, verification

Notes for future work, written 2026-07-30. Not a plan of record; these are the four gaps
between where the `sim_*` dashboards are today and where they need to be.

> **Status, 2026-07-30.** Steps 1–3 of the suggested order are **built**: activation
> counting, energy measurement, and the `--audit` flag with the offensive relevance
> classifier. §3, §4 and §5 below describe the design; see *What is built* at the bottom
> for what actually shipped and what is still outstanding. The defensive half of the audit
> remains blocked on a defender skill axis.

Context: `DESIGN.md` is the architecture, `grafana/DASHBOARD_NOTES.md` is the per-dashboard
reference (its second half covers the `sim_*` ones), and `../../balance-simulation/NOTES.md`
is the long-term vision. Nothing here contradicts those — it is the backlog they imply.

---

## 1. Display parity with the non-sim dashboards

The `sim_*` dashboards are currently *thinner* than the SQL-modelled ones they are meant to
retire. Three sim dashboards with 4–7 panels each replace four hand-built dashboards whose
panel and control surface is much wider. The retirement is not honest until the sim side can
answer the same questions.

**What exists today**

| Dashboard | Panels | Variables |
|---|---|---|
| `sim_dps_ttk_explorer` | text, Run table, Strength-by-role bar, TTK histogram, Modifier breakdown table, Per-skill strength bar, Builds table | `realm`, `run`, `role`, `target` |
| `sim_patch_diff` | text, Runs table, Summary stat, Mean-delta-by-role bar, Biggest movers bar, Per-build deltas table | `realm`, `run_a`, `run_b` |
| `sim_empirical_overlay` | text, Sim-DPS-vs-live-KDR xychart, Role table, Skill table | `realm`, `run` |

**What the non-sim side has that the sim side does not**

- **`weapons_range.json`** — the whole "weapon axis" view: DPS range no-runes vs all-runes,
  per-rune individual contribution, damage-per-hit min/max roll range, TTK-vs-every-role
  table, hits-to-kill table. The sim has `WEAPONS` and `RUNES` scopes that produce exactly
  this data and no dashboard that reads them. **This is the biggest single gap** — probably
  a new `sim_weapons_range` generated dashboard.
- **`weapons_simulator.json`** — side-by-side comparison of up to 8 named builds
  (`build1_weapon`/`build1_runes`/`build1_skills` … ×8), with bar-plus-error-bar DPS, TTK vs
  all roles, and summary/HTK tables. The sim equivalent is "pick N `build_fingerprint`s from
  a run and compare them", which is a genuinely different and easier query — a build picker
  rather than a build *constructor*. Worth building as `sim_build_compare`.
- **Distribution panels.** The old dashboards lean on `ae3e-plotly-panel` for DPS/TTK/HTK
  density across the whole combination space. The sim has one `histogram` of TTK. It should
  have the same three distributions, and it can do them honestly (measured, not modelled)
  — plus a fourth the old ones could never draw: the *within-build* iteration spread, since
  percentiles already ride in `sim_result.extras`.
- **Hits-to-kill.** `sim_result.hits_to_kill` is recorded and no panel shows it. Both
  `weapons_range` and `weapons_simulator` have dedicated HTK tables.
- **Damage breakdown stacked bar.** `ttk_all_valid_builds` panel 2 stacks the damage
  contributions of the best build per weapon. The sim's per-modifier breakdown lives in
  `extras` and is currently only a table.
- **Roll min/max.** The old dashboards sweep the weapon damage *roll* (`roll` variable,
  min/max) and draw the resulting range as error bars. The sim has no roll axis at all —
  see §2.

**Constraint that must not be violated:** these are generated by
`grafana/generate_sim_dashboards.py`. Every new panel goes in the generator, never in the
JSON. The 200KB of unmaintainable SQL is exactly what the simulator exists to retire, and
hand-editing one sim dashboard reintroduces it.

## 2. Permutation coverage the old dashboards give that the sim does not

The SQL dashboards enumerate their space in SQL, so their space is free; the sim pays real
wall clock per matchup. That is the whole tension. But there are axes the old dashboards
cover that the sim currently has *no way* to cover, and those are the ones that block
retirement:

- **Weapon damage roll (min/max).** Every old dashboard has a `roll` variable and treats
  damage as a min–max range, drawn as error bars. The sim measures a single deterministic
  roll — **rolls are not random**, confirmed against `SimEquipment`, so this is purely a
  coverage gap and never a source of run-to-run noise. Patch diffs are safe. If the
  min/max range is wanted back it has to become an explicit axis; until then every sim
  figure is one point on a range the old dashboards showed whole.
- **Runes × skills together.** `RuneAxis` is deliberately excluded from `FULL`
  (`SimScope.java`). `dps_ttk_density` sweeps runes and skills simultaneously via
  `active_runes` + `active_skills` multi-variables. So there is a class of question — "does
  this rune change which skill is best" — that the sim structurally cannot answer today.
  Accept it explicitly, or add a narrow `SKILLS_RUNES` tier scoped to a curated skill list
  (see §3) so it stays affordable.
- **Multi-rune sets.** `RuneAxis.ONE_AT_A_TIME` yields one rune plus baseline.
  `weapons_range` compares no-runes vs *all four* damage runes. A "full damage rune set"
  option is cheap to add (one extra set per weapon) and covers the headline old-dashboard
  comparison.
- **Defender builds.** Targets carry no skills (`BalanceCatalog.enumerateTargets`). The old
  dashboards model defender-side `fortify`/`deflection` via override variables. Until the
  defender axis exists, `mutual` runs are a swept attacker vs a bare role — fine, but the
  overlay dashboard's "theory vs practice" comparison inherits that bias and should say so.
- **Target armour tiers.** Old side has `target_hp` multi + `target_defense` +
  `target_defense_level` + `target_ruby_gems`. Sim has `NO_ARMOR` / `ROLE_ARMOR`. Reinforced
  and gemmed tiers are a straightforward `SimEquipment` addition and multiply the space by a
  small constant, unlike the skill axis.
- **Interleaving already solved the early-stop problem** (`interleaveByRole`) — so a `FULL`
  sweep stopped early is a uniform sample. Keep that property in mind when adding axes: any
  new axis should be interleaved too, or an early stop becomes biased along the new axis.

## 3. The skill relevance audit — generating the exclusion lists

This is the centrepiece. The exclusion lists are known-in-principle to a human who knows the
skills; what makes them worth generating is that organising ~150 skills by hand is slow and
the result would not be checkable. So: **the sim measures relevance empirically and emits an
auditable list, a human reviews it, and the reviewed list goes into config.**

### The rule

Run each skill in isolation (the `SKILLS` scope already does exactly this) and compare
against the matching empty-slot baseline — same role, same weapon, same target, same run.

- **Offensive-inert** — the skill on the *attacker* produces no increase in damage, i.e. no
  decrease in TTK, versus baseline. Exclude from the attacking side of non-mutual sweeps.
- **Defensive-inert** — the skill on the *defender* produces no decrease in incoming damage,
  i.e. no increase in TTK, versus baseline. Exclude from the defending side.
- **Excluded from `mutual`** — the intersection: a skill on *both* lists moves nothing in
  either direction and cannot matter when both sides fight.

Derive the mutual list rather than storing it as a third list, so it cannot drift out of
sync with the two it comes from.

### Three buckets, not two

The critical distinction, and the reason the word "auditable" is doing real work here: a
skill can measure inert because it genuinely does nothing, **or because the harness cannot
drive it**. Collapsing those bakes a harness bug into config permanently and silently.

| Bucket | Meaning | Action |
|---|---|---|
| **Relevant** | fired, moved the number | keep in the sweep |
| **Inert** | fired ≥ N times, did not move the number | exclude — a real finding about the game |
| **Undrivable** | never fired | exclude, but flag as a *harness gap*, not a balance finding |

Undrivable is a bug list for the rotation policy, not a balance list. Bow archetypes are the
known deliberate case; anything else landing there is a defect. These must be separately
labelled in the output — never merged into "inert".

### Deciding "no change"

Rolls are deterministic, but duels still vary by tick timing across Monte-Carlo iterations,
so the comparison needs a threshold rather than exact equality:

- Compare mean TTK (and mean DPS) against baseline with an explicit epsilon, and record the
  epsilon in the artifact. A skill is inert only if the delta is inside the band.
- Prefer requiring the delta to be inside the band **across every target** the run swept, not
  just on aggregate — a skill that only matters versus armoured targets is not inert.
- Record the iteration count behind each verdict. A verdict from three iterations is not the
  same claim as one from fifty, and the reviewer needs to see which they are looking at.
- Sweep the skill at its full level range. A skill inert at level 1 and live at level 5 is
  relevant; classify on the *best* level, and record which level produced it.

### The `--audit` flag

A flag on `/simulate` (rather than a new scope) that runs the `SKILLS` sweep and, instead of
only writing `sim_result` rows, post-processes them into the classification above.

Rough shape: `/simulate SKILLS ONE_WAY --audit`. Notes:

- Argument parsing today is positional (`args[0]` scope, `args[1]` scenario) with an explicit
  refusal on anything unrecognised. Adding a flag means parsing trailing `--`-prefixed
  arguments separately and keeping that refuse-don't-default behaviour — a mistyped
  `--audti` must be an error, not a silently ordinary run.
- The audit is a *reporting mode over a normal sweep*, so the `sim_result` rows are written
  exactly as usual and the audit artifact is derived. That keeps the audit re-derivable from
  stored data and lets an old run be re-audited with a different epsilon without re-running
  any duels. **Strongly prefer this over computing verdicts only in-flight.**
- Tab completion should offer the flag, same reasoning as the existing scope/scenario
  completion.

### The defensive half needs a defender skill axis first

Blocker worth stating plainly: `BalanceCatalog.enumerateTargets` gives targets no skills at
all — `target_skills` is empty by design. **The defensive-inert list cannot be measured until
defenders can carry a skill.** The offensive list is measurable today.

Two options: a narrow defender-side variant of the `SKILLS` scope (fixed baseline attacker,
one skill on the defender, swept) — which is the cheap targeted answer and probably right —
or the general defender-build axis noted in §2, which is much more expensive. The audit only
needs the former.

So the offensive list can be generated now; the defensive list and therefore the mutual
intersection are gated on that work.

### Output artifact

Needs to serve two readers — a human reviewing it, and the config that consumes it.

Per skill, at minimum: skill name, role, slot, archetype, marker interfaces, best level,
delta vs baseline per target, iteration count, activation attempts/successes, failure reasons,
verdict, and bucket. Emit as a file the reviewer can read and diff (and paste from), and keep
the same rows queryable for a dashboard panel.

Also record, on the artifact itself: the `sim_run` id it came from, the `balance_config`
digest, the epsilon, and the skill filter in force. A relevance verdict is only true for the
config it was measured under.

### Staleness is the main long-term risk

A skill excluded once stays excluded forever, including after someone buffs it from zero —
at which point the sim silently stops measuring the thing that changed. Mitigations:

- Store the `balance_config` digest with the list; warn loudly when the live digest differs
  from the one the exclusions were generated under.
- Re-run the audit as a matter of course when skill config changes, and diff the buckets. An
  audit diff ("3 skills became relevant, 1 became inert") is a genuinely useful balance
  artifact in its own right, not just hygiene.
- Never let the exclusion list be generated and applied in one step without human review.
  Generate → review → commit to config.

## 4. Marker-based prefilter (cheap prior, before the audit)

The audit is empirical but costs a full `SKILLS` sweep. The existing marker interfaces give a
cheap a-priori narrowing, and one of the audit's side benefits is checking whether those
markers are accurate.

Current default is `SimSkillFilter.OFFENSIVE`: exercisable (non-bow) ∧ `instanceof
OffensiveSkill`. Two weaknesses — `OffensiveSkill` is author-maintained, so an omission
silently drops a skill; and it admits skills that move no measured column (pure knockback,
pure CC), which burn duel time producing baseline-identical rows.

A narrower filter stated positively — **skills that touch damage or energy** — is buildable
from markers that already exist in `champions/.../skills/types/`: `DamageSkill`,
`EnergySkill`, `EnergyChannelSkill`. Adjacent and worth deciding on: `ChannelSkill`
(interacts with `channel_hold_ticks`), `HealthSkill` (moves effective HP, so it moves TTK
defensively), `DefensiveSkill` (matters only under `mutual`).

```
exercisable(skill) && (skill instanceof DamageSkill
                    || skill instanceof EnergySkill
                    || skill instanceof EnergyChannelSkill)
```

- Not a superset or subset of `OFFENSIVE` — it admits some unmarked energy drains and rejects
  some marked-offensive CC. Runs under the two filters are therefore not comparable; the
  filter is part of `config_hash`, so the dashboards will correctly refuse to diff them.
- **The audit checks the markers.** Any skill the audit finds relevant that carries no
  `DamageSkill`/`EnergySkill` marker is a champions-side marker bug. Any skill carrying
  `DamageSkill` that the audit finds inert is either broken or undrivable. Both lists are
  valuable output and neither is obtainable from the markers alone.
- **Energy is barely measured.** `SimResultRow` carries one `energyLimited` boolean. If the
  sweep is scoped *by* energy relevance, results need energy columns worth reading: energy
  spent, mean energy floor, time stalled on energy, casts attempted vs landed. Otherwise the
  filter selects for a dimension nothing can display, and "energy-inert" is unmeasurable —
  note that the §3 rule as written only tests damage/TTK, so an energy-only skill would be
  classified inert on a dimension the audit never looked at. **Either add the energy columns
  or state that the audit's verdict is damage-only.**
- Keep a hand-written allowlist as an escape hatch — some sweeps want ten named skills.

## 5. Other verification worth having

Beyond the audit, which subsumes most of what per-skill verification needs:

1. **Activation counting is a prerequisite for the audit**, not a separate nicety — the
   inert/undrivable split is exactly activation count. Record attempts, successes, and
   failure reason (cooldown, energy, wrong weapon held, range, no target, declined). Check
   whether `SimTrace` can already carry this.
2. **Archetype coverage report.** Group admitted skills by `ActivationArchetype` and report
   fire rate per archetype. A whole archetype at 0% is a single rotation-policy hole worth
   more than any individual skill investigation. Bow is the known deliberate gap; anything
   else at 0% is a defect.
3. **Config-value sanity check.** For a handful of known skills, compare measured per-hit
   damage against configured damage at that level. Not an assertion — the sim measures rather
   than models — but a large divergence means the skill or the harness is wrong.
4. **Manual spot-checks.** For anything landing in *undrivable*, activate it by hand on a dev
   server. The automated checks find candidates; only a human separates "broken in the game"
   from "broken in the harness".

The greedy rotation is the theoretical ceiling by design, so a skill firing less often than
greedy predicts is not automatically a bug — but a skill firing *never* is.

## Suggested order

1. **Activation counting** (§5.1). Prerequisite for the audit — without it, inert and
   undrivable are indistinguishable and the exclusion lists are untrustworthy.
2. **Energy result columns** (§4), or an explicit decision that audit verdicts are
   damage-only. Needed before the lists mean what they say.
3. **The offensive audit + `--audit` flag** (§3). Measurable today; produces the first real
   exclusion list. Review it by hand, then commit to config.
4. **Defender skill axis, then the defensive audit and the mutual intersection** (§3). The
   defensive half is blocked on this and nothing else.
5. **§1 `sim_weapons_range` and the missing distribution/HTK panels** — cheap, reads data
   that already exists.
6. **§2 armour tiers, multi-rune sets, roll axis** — coverage, not correctness. Roll is
   deliberately last: it is a deterministic single point, so nothing is currently wrong,
   only narrower than the old dashboards.
7. **§1 `sim_build_compare`**, replacing `weapons_simulator`.

Only after 1–7 is retiring the SQL dashboards defensible.

Steps 1–3 are the ones that make the exclusion lists exist; everything after is display and
coverage.

## What is built (2026-07-30)

Steps 1–3 shipped. Engine version bumped to `phase3-actives-3`, because a `SKILLS` run at
`-2` has no baseline rows and cannot be audited.

**Activation counting** — `SimActivationOutcome`, `SimSkillLedger`. The rotation reports
every press (`GreedyRotationPolicy.notePress`); `SimRecorder.onUseSkill` classifies the
chain's verdict at `MONITOR` as SUCCESS / COOLDOWN / ENERGY / DECLINED. Both sides are
tracked, so the defensive audit will not need a re-run to get its data. Lands in
`sim_result.extras.activations`.

**Energy measurement** — `SimEnergyLedger`. `DegenerateEnergyEvent` and
`RegenerateEnergyEvent` observed at `MONITOR` (post-cancel, post-rescale, so the figures are
what was actually applied), bucketed by cause, plus current/max sampled at each event.
Lands in `sim_result.extras.energy` as per-duel means. `energy_limited` keeps its original
narrower meaning and is unchanged.

**The audit** — `balancesim.audit` package: `SkillRelevanceAudit` (classifier),
`AuditThresholds`, `SkillVerdict`, `SkillRelevanceBucket`, `SkillAuditReport`. Run it with
`/simulate SKILLS ONE_WAY --audit`. Writes a commented YAML artifact to the plugin's
`audits/` folder — exclusion lists valid as config, every line carrying its evidence.
Generate → review → commit; it never writes config itself.

Nine unit tests in `SkillRelevanceAuditTest` cover the decisions, including the two that
motivated making energy first-class: **Null Blade** (siphons energy, deals no damage) and
**Energy Pool** (raises max energy, moves none) both classify RELEVANT and are flagged
`[ENERGY ONLY]`. A damage-only audit would have called both inert.

### Decisions worth knowing about

- **`SimScope.SKILLS` now enumerates skill-less baselines** alongside its single-skill
  builds. It previously had no zero point, which made the tier's own stated purpose — a
  readable per-skill strength curve — unachievable and left the audit with nothing to
  subtract. Adding rows changes no existing figure.
- **Significance is judged per matchup, not on pooled figures**, so a skill that only
  matters against armour is not averaged below the threshold by the targets it does not
  affect.
- **A driven skill that fired but fired rarely** (< `minSuccesses`, default 3) reports
  UNDRIVABLE rather than INERT. An inert verdict claims the skill had its chance; two
  successes do not support that.
- **A matchup where one side killed and the other timed out** is relevant by definition —
  every numeric delta is zero there, and that is the case that most obviously must not be
  missed.
- **The audit runs on cancelled and failed runs too.** A `FULL` audit is not expected to
  finish and stopping it early is the normal way to use it; the enumeration is interleaved
  by role, so an early stop is uniformly thinner rather than biased.

### Known limits, carried in the artifact header

- **Each skill is measured alone against a bare baseline.** An energy skill has nothing to
  enable in a build with no other skills, so `inert` means "cannot matter alone", not
  "cannot ever matter". This is the one place the tiered scope and the audit's question
  genuinely pull against each other.
- **Passives are exempt from the firing test** — no button, so no attempts. A passive whose
  listener never runs is indistinguishable from one that runs and does nothing; both land
  in INERT. Closing this needs per-skill damage attribution, which the pipeline's reason
  labels could support but do not yet.
- **`ONE_WAY` says nothing about defensive value**, and the artifact says so when the
  scenario is one-way.

### Still outstanding

1. **Defender skill axis** → the defensive-inert list and the mutual intersection.
   `BalanceCatalog.enumerateTargets` still gives targets no skills.
2. **Re-audit from stored rows.** Verdicts are currently derived in-flight from the same
   aggregates the rows are built from. The classifier is a pure function over aggregates, so
   feeding it from SQL is a contained change — worth doing so an old run can be re-audited
   at a different epsilon without re-running duels.
3. **Thresholds are not yet config.** `AuditThresholds.defaults()` is hardcoded; the
   artifact records what was used, so nothing is ambiguous, but a reviewer cannot yet re-run
   at a different epsilon without a rebuild.
4. **No dashboard panel** reads `extras.activations` or `extras.energy` yet — see §1.
